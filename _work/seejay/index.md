## **Designing in the browser, not around it**

The project began with hand sketches, but those sketches were treated as a bridge rather than a deliverable. Their purpose was to clarify structure, hierarchy, and possible interface patterns quickly, before investing too much effort in visual polish.

From there, the sketches became HTML wireframes. This shift mattered because the design could be evaluated as a system of behaviours rather than a collection of screenshots. Navigation, content density, spacing, and responsive behaviour could be tested in the environment where the product would actually live.

Working this way also reduced the distance between design intention and implementation. Instead of asking development to translate a static artifact, the redesign produced a shared object that designers, developers, and stakeholders could inspect together.

## **Atomic design as an operating model**

The redesign organised the interface using the atomic design methodology popularised by Brad Frost: atoms, molecules, and organisms. This gave the project a vocabulary for discussing the site as a reusable system rather than as a sequence of isolated pages.

Atoms defined the smallest interface elements. Molecules combined those elements into functional units. Organisms assembled those units into larger sections of the experience. This structure made the redesign easier to reason about, because each decision had a place in the system.

It also made the work more sustainable. When an interface is designed as a set of reusable parts, consistency stops depending on memory or manual duplication. The system carries the decisions forward.

## **Replacing approval theatre with working evidence**

One of the most important outcomes of the process was cultural. By moving away from static previews, the redesign avoided the theatre of asking stakeholders to approve an image of a website. Instead, decisions could be grounded in working prototypes.

This made feedback more practical. Stakeholders could react to navigation, hierarchy, and behaviour in a browser. Designers could identify issues earlier. Developers could understand constraints before the handoff became a bottleneck.

The redesign therefore became as much a process improvement as a visual one: a way to make the team’s conversations more concrete, and to make the final product less dependent on interpretation.
